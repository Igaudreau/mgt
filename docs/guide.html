INSTALLATION

It is assumed that you have unpacked the mg tarball in a directory called mg in your home directory. In the .cshrc file in your home directory insert the lines

setenv mg ~/mg
source $mg/_cshrc

This sets up the environment variables for mg and the data directories (note that you need to be running csh or tcsh for any of this to work). The model files (*.dsb) files are written to these directories. (see write command). These are set to ~mg/mg_g/data, ~mg/mg_m/data and ~/mg_mv/data in _cshrc, but you might want to change this.It also sets the environment variable PRECISION, which determines the precision. The default is SINGLE,  but you can change this by uncommenting/commenting the appropriate lines. 

The directories in mg are

src   - contains the generic source files and the directory linux for object files.
lib   - contains the libraries (muvi, parcsmp, parcmpi, smp).
bin   - contains the excutables (mg_g, mg_m).
mg_g  - working directory for mg_g.
mg_m  - working directory for mg_m.
mg_mv  - working directory for mg_mv.
docs  - documentation.

The working directories, mg_g, mg_m and mg_mv do not have to be in the mg directory: they can be anywhere.

First create the libraries by doing

Createlib

in the mg directory. Note that if you later change the precision, then you have to remake the libraries with

Clearall
Createlib

There three versions of the code:

MG_G  - Gas dynamics with viscosity and a k-epsilon turbulence model.
MG_M  - Ideal MHD.
MG_MV - MHD with resistivity and viscosity.

Each of these is in its own directory. You can make them by going to the relevant directory and doing

makemg smp
or
makemg mpi

to make either the smp or mpi versions. This creates mg_g,  mg_m or mg_mv depending on the directory you are in. In order to make the mpi version you will need a working implementation of mpi (this is set to mpicxx in mg/_cshrc). Note that the executables (mg_g, mg_m or mg_mv) will be in the directory mg/bin and the object files in mg/src/linux. The linker may complain that it cannot find the X11 libraries. These are defined by the environment variable X11_libs, which is set to -lX11 in _cshrc. On some installations you may have to specify these explicitly by setting X11_libs to something like /usr/X11R6/lib/libX11.a. You must also make sure that you have installed readline and ncurses.
Note that, in the interest of speed, the arrays in the cell structures are static with sizes determined by MAXD (maximum number of dimensions) and MAXQ (maximum number of solution variables). These are set in the file struct.h. It is a good idea to keep these as small as possible for the particular application. The code will complain if they are too small.

To run mg_g, mg_m or mg_mv in scalar mode type

mg_g
or
mg_m
or mg_mv

in the the relevant directory (if you have just created them for the first time, you might have to type ../bin/mg_g,  ../bin/mg_m or ../bin/mg_m). This will give the mg_g, mg_m  or mg_mv prompt

MG_G>
or
MG_M>
or
MG_MV>


To quit type q at the command prompt.

From now on we will assume that you are running mg_g. Where a command is special to mg_m or mg_mv, this is indicated.
 

INITIAL CONDITIONS

At the prompt type

MG_G>$read filename

where the initial conditions are in a file filename.dat. e.g. the file sod.dat sets up the Sod problem. It contains

START "1 dimensional sod test" ! START command and title
 LEVELS 1     ! Number of levels (numbered from 0)
 XYZ 1      ! Geometry and number of dimensions
  X 100 -1 1 FREE   ! X No of cells, domain and boundary condition
 CASE SOD     ! Case
 SCALARS 2     ! No of scalars (optional, default=1)
END       ! End of START command

Note that everything on a line after a ! is a comment. These commands will be echoed as the file is read in. In fact reading a .dat file with $read produces exactly the same effect as typing the these commands at the command prompt.

For multidimensions you might have

  XYZ 2
  X 1000 0.0 5.0 SYMMETRIC-FREE ! Specs for X
  Y 1000 0.0 5.0 SYMMETRIC-FREE ! Specs for Y

Here the left boundaries have symmetry and the right boundaries are free (zero normal gradient).

INITIAL SOLUTION

The initial solution is set by the routine usrqis using the case determined by the CASE command. usrqis is given the position of the cell centre and must return the desired conserved variables in that cell. There are two modes of initialisation for adaptive grids, fast and slow, invoked by the FAST (DEFAULT) and SLOW commands. These must be issued before the START command.In fast mode usrqis is first called for each cell on the two coarsest levels (0 and 1) and the solutions are then compared to determine whether the cell should be refined to level 2. This process is repeated until the finest level is reached and the solutions are then merged to ensure that the solution in a coarse cell is the average of that in its children. This works fine unless level 1 is so coarse that it does not capture some region that needs to be refined. In that case it is necessary to use slow initialisation, which calls usrqis for potential cells on all levels. The potential cells are not created unless they are needed, so this does not consume any more memory, but it can be very slow if there are a large number of levels.

GEOMETRIES

Three geometries, XYZ (cartesian), RZP (cylindrical polars) and RTP (spherical polars) are supported. XYZ is available in 1, 2 and 3 dimensions, RZP in 1, 2 dimensions and RTP in 1 dimension.

For RZP and RTP the r=0 boundary must be symmetric e.g.

  RZP 2
  R 1000 0.0 5.0 SYMMETRIC-FREE ! Specs for R
  Z 1000 0.0 5.0 FREE    ! Specs for Z

imposes a symmetry boundary on r=0 and free elsewhere. Note FREE or SYMMETRIC imposes those boundary conditions at both ends (i.e. not FREE-FREE or SYMMETRIC-SYMMETRIC).

Other possible boundary conditions are PERIODIC, FIX and WALL e.g. XYZ 2

  X 1000 0.0 5.0 FIX    ! Specs for X
  Y 1000 0.0 5.0 PERIODIC   ! Specs for Y

imposes fixed boundary conditions on the x boundaries and periodic boundary conditions on the y boundary. For obvious reasons, PERIODIC cannot be combined with another boundary condition for the same coordinate. The FIX boundary condition imposes fixed conditions. Exactly which variables are fixed can be set in the routine usrbd in usr.c. WALL (MG_G  and MG_MV only) is the same as symmetry except that it also imposes no slip for viscous problems.

The domain and boundary conditions set up by the start command are not set in stone: the size of the domain can be reduced by the NEWDOM command and the boundary conditions can be changed by the BOUNDL and BOUNDR commands. For example, if the original x range and boundary conditions were

    X 1000 0.0 5.0 FIX

Then these could be changed to

  X 500 0.0 2.5  FIX-FREE

by

  NEWDOM 0 2.5
  BOUNDR 1 FIX

SCALARS

The SCALAR subcommand of the START command defines the number of scalars. By default these are advected at the fluid velocity, but some or all of them can be defined to be non-advecting by e.g.

  SCALARS 2 ADVECT 1

This defines two scalars of which the first is advected and second is not. Note that by default there is always one scalar, which is advected.

 TURBULENCE MODEL

The mg_g code contains a k-epsilon turbulence model, which is invoked by the KEPS command. This has to be executed before the START command.  The dimensionless constants in this model are standard and are set in the routine usrkeps. The equations for this model are given in k-epsilon-equations.

INTERNAL ENERGY

The code works with the conserved variables and this can lead to errors in the internal energy when the internal energy is small compared to the kinetic and magnetic energies. This has no effect on the dynamics, but it does mean that the temperature is inaccurate in such regions. In order to cope with this, there is a facility for solving the internal energy equation in addition to the equation for the total energy. This is invoked by the command INTEN, which must be invoked before the START command. The internal energy is stored in pa[iqei] and qa[iqie] (see usrqis).

 GRAVITY

The mg_g and mg_m codes include self-gravity, which can be invoked with the command

grav

at any time during the calculation. It can be switched off by grav. The  gravitational potential is calculated  using a full approximation multigrid. This is controlled by the parameters, NREL - the number of relaxations on each level and NORMRAT - the convergence tolerance for the multigrid. These are set by the commands


nrel number

and

normrat value

The default values are nrel = 5, normrat = 0.25, which should be appropriate in most cases.

By default the potential is set to zero at FREE and FIXED and its derivative to zero at SYMMETRIC boundaries. However, this might not accurate if there is a significant amount of mass near the boundaries or the domain is small. In such cases, one can invoke the calculation of the boundary potential by

boundpot

at any time during the calculation. It can be switched off by noboundpot.This computes the boundary potential at FREE and FIXED boundaries by summing over all interior cells on level levb. levb is set by

levb  level

The default is levb = 1. This is not implemented in a particularly efficient way, so it is wise to keep levb as small as possible.

TIME INTEGRATION

To advance the solution type

MG_G>march nsteps

where nsteps is the number of timesteps to be executed. You can also set it to stop at time targettime with the command

MG_G>target targettime
 
e.g. for sod you could do

MG_G>target 0.1
MG_G>march 100

This will stop at time = 0.1. Note that if the given number of steps is not enough to reach the targettime, it will stop after the given number of steps and report that the target time has not been reached.

CHECKPOINTING

At any time the current model can be written to the data directory $mg_g_data by

MG_G>write file

In scalar mode this writes files file.h.dsb and file000.dsb. In parallel mode the files are file.h.dsb, file.n.dsb with n= 0..npe where npe is the number of processors.

The model can be read in by

  MG_G>read file

Note that the model can be read in with a different number of processors than that with which it was created.

GRAPHICS

First set up a graphics window by reading the graphics setup file x.dat

MG_G>$read x

If you get weird colours in 2D graphics, edit x.dat and replace the line

open a x

by

open a x_tecra

Now you can choose to plot e.g. the x velocity by

MG_G>plot u1

Then plot it by

MG_G>p

By default this puts markers at each grid point and joins them with a line. The markers can be switched off by

MG_G>marker 0

The line can be switched off by

MG_G>noline

The markers can be switched on again by

MG_G>marker n

where n=1,2,3 or 4 for different marker styles. The line can be switched on by

MG_G>line 1

By default graphs are plotted on top of each other. A graph can be erased by

MG_G>er

By default, the x range is equal to the size of the domain. It can be set to xmin < x < xmax by

MG_G>xr xmin xmax

The default can be restored by

MG_G>noxr

By default, the range for a variable q (e.g. u1) is qmin < q < qmax where qmin and qmax are the minimum and maximum values that occur. This can be reset by

MG_G>qr nqmin nqmax

where nqmin - nqmax is the desired range.

The default can be restored by

MG_G>noqr

The graphics window can be split by

MG_G>selectw w

where w=t or b for a window at the top or bottom. All subsequent plotting occurs in the selected window until another window is selected. The whole window can be selected by

MG_G>selectw whole

A ps file of a graph can be created once a graphics window has been set up by $read x. Type

MG_G>open b ps_rgb

Then execute a set of graphics commands e.g.

MG_G>plot u1 p

Note that this draws contours by default unless you have opened an x window. To suppress these do

MG_G> nocontour

before plotting.

Now close the ps file

MG_G>close b

This creates a file b.ps in the current directory, but it lacks a bounding box and various other essentials. It needs to be completed by

MG_G>$ plot b output

This creates a file output.ps in the current directory.
 

COMMAND INTERPRETER

MG_G is controlled by a command interpreter and the above are examples of the available commands. These fall into three categories

SYSTEM COMMANDS

These are preceded by $ followed by a space. The commands consist of the usual shell commands e.g.

MG_G>$ ls *

will list files in the current directory. It is also possible to spawn a shell by

MG_G>$ csh

You can then execute shell commands and when you have finished type

exit

to return to mg_m.

There is also a command $log filename which writes all input commands to a file filename.log.

The most common plot variables (chosen by plot name) are

Once a plot variable is defined by plot, this variable is plotted until another is chosen.

You can also draw streamlines or field lines using the stream command. This is of the form

MG_G>stream num x0 y0 z0 dx dy dz
This places num starting points starting with x0, y0, z0 and spaced by dx, dy, dz. The lines are drawn from these points. The file streamrz.dat contains an example of this. For adaptive calculations you need to do

MG_G>levs 1 maxlev

where maxlev is the maximum level (see generic commands). Once you have done this, you plot streamlines by doing

MG_G>v

or fieldlines (MG_M or MG_MV) by

MG_G>b

By default, the v and b show arrows. You can return to this with

MG_G>arrow

Note that when using very fine grids, the velocity arrows can be very small. You can choose to plot them at intervals of n cells by

MG_G>vrate n

You can also change the scale of the arrows by

MG_G>vscale value

Value determine the length of the arrows (default 1). The same commands also affect the magnetic field arrows in MG_M or MG_MV.

There are also other commands, some of which are used in the x.dat file. The only one you might want to change in the x.dat file is the paper size command

paper 6.0 6.0

Although plot is a muvi command, its argument (the plot item) is accessible to the user. The routine usrps in the file usr.c is given the argument of plot in the string variable item. The user can use this to define different plot items using the existing templates.

It is possible to plot a data file using the readxq command. For example

MG_G>readxq time

plots the data in the file time.xq. The file consists of a title for the graph and the abscissa and ordinate, together with a list of pairs of data values, "x" and "y". It plots the graph of y against x. The file time.xq gives an example. It is also possible to plot two and three dimensional graphs: help readxq gives information on this.

The current plot can be exported to a file by

MG_G>export filename p

This produces a copy of the current plot in a file filename.xq (help export gives more information). This file can be read in by readxq.


MG_G>help topics

lists all graphics commands. Help on an individual command can be got by  help command e.g.

MG_G>help plot

gives help on the plot command.

These are defined in the routine

where key is a string variable containing the command. The user can add additional commands with or without arguments. Use the existing commands as templates. The current commands are

Commands can have a number of arguments, which can be integer, real or strings. These are obtained from the input by get_i, get_r or get_n. When adding commands, make sure that the correct routine is used.

The input is almost completely free format - the arguments to a command need not be on the same line as the command e.g.

MG_G>plot u1 p

is the same as

MG_G>plot
MG_G>u1
MG_G>p

The command line can also be edited using the usual commands(e.g. ^K etc) and a history is kept which can be accessed by the up/down arrow keys as in the shell. To see a full description of the facilities look at the man page for readline. There are, however, some limitations: lines must not be longer than 100 characters;  quoted strings must be on one line; system commands must be on one line.

 USER MODULE

The user routines are in the file usr.c. There are a number of these routines that the user is likely to want to change:

usrqis

This is used to set up the initial solution. It is given the x, y, z coordinates of a cell in xc(nd) with xc(0) = x, xc(1) = y, xc(2) = z. It must return the initial values of the primitive variables in pa according to the following scheme

pa[iqd]     density of fluid
pa[iqu0+1]  x velocity of fluid
pa[iqu0+2)  y velocity of fluid
pa[iqu0+3]  z velocity of fluid
pa[iqe]     pressure of fluid
pa[iqb0+1]  x component of magnetic field (MG_M only)
pa[iqb0+2]  y component of magnetic field (MG_M only)
pa[iqb0+3]  z component of magnetic field (MG_M only)
pa[iqk]     turbulent energy per unit mass (KEPS only)
pa[iqeps]   turbulent dissipation rate per unit mass (KEPS only)
pa[iqie]    internal energy per unit volume (only if INTEN command is invoked)
pa[iqal0+1] value of scalar 1
pa[iqal0+2] value of scalar 2 etc
Note that in MG_G the number of velocity components is equal to the number of dimensions, but in MG_M and MG_MV all three velocities exist whatever the number of dimensions. It contains a set of else if clauses that choose the particular initial data according to the value of case given in the start command. The size of this array is determined by MAXQ in struct.h.

usrss

This is given the density and pressure (mg_g) density, pressure and filed components (mg_m). It must return the sound speed(s).

usrqp

This is given the primitive variables in pa and must return the conserved variables in qa. The conservative variables are as follows

qa[iqd]     density of fluid
qa[iqu0+1]  x momentum of fluid
qa[iqu0+2)  y momentum of fluid
qa[iqu0+3]  z momentum of fluid
qa[iqe]     total energy of fluid per unit volume (internal + kinetic + magnetic)
qa[iqb0+1]  x component of magnetic field (MG_M only)
qa[iqb0+2]  y component of magnetic field (MG_M only)
qa[iqb0+3]  z component of magnetic field (MG_M only)
qa[iqk]     turbulent energy per unit volume (KEPS only)
qa[iqeps]   turbulent dissipation rate per unit volume (KEPS only)
qa[iqie]    internal energy per unit volume (only if INTEN command is invoked)
qa[iqal0+1] mass of scalar 1 per unit volume (i.e. density times  pa[iqal0+1])
qa[iqal0+2] value of scalar 2 etc

usrpq

This is given the conserved variables in qa and must return the primitive variables in pa. It must be consistent with usrqp.

usrfxq

This fixes up the conserved variables to ensure that the internal energy and density are positive. The density is set to dfloor if it is less than dfloor. The internal energy is set to (pfloor + 1) times the total kinetic and magnetic energy (MG_M, MG_MV). The routine is given the cell pointer, so that cptr->xc gives the cell positions. It can therefore be used to impose particular values in given regions.

usrfxp

This fixes up the primitive variables to ensure that the pressure and density are positive. It follows the same rules as usrfxq and should be consistent with it.

usrps

This is given the string item which is determined by the plot command e.g. plot u1 sets item = "U1". The user can define new plotting items using the existing code as a template.

usrsaf

This is given the values of the primitive variables and must return the corresponding value of the source term in the array so according to the following scheme

so[iqd]     mass source for fluid
so[iqu0+1]  x momentum source for fluid
so[iqu0+2]  y momentum source for fluid
so[iqu0+3]  z momentum source for fluid
so[iqe]     energy source for fluid
so[iqal0+1] source for scalar 1
so[iqal0+2] source for scalar 2 etc

In principle you could also have a source for the magnetic field in MG_M or MG_MV, but this would be weird. Note that usrsaf is also given the cell position in cptr->xc[nd] and the and conservative variables at the old time in cptr->qa.

usrref

This routine calculates a reference solution based on the solution in the cell. This is used in usrqsol to decide upon refinement.

usrqsol

This routine decides whether a cell should be refined or not. It is given the level and cell which is to be refined or derefined. It should return qsol = badcell if the cell needs to be refined, qsol = good otherwise. The conservative solution for the cell is in cptr->qa and cptr->pa contains the solution mapped down from the parent cell. These can then be compared in order to determine whether or not the cell should be refined.

usrte

This function is given the primitive variables in pa and must return the fluid temperature.

usrmu

This function is given the primitive variables in pa and must return the fluid viscosity and diffusion coefficients.

usrkeps

This function sets the dimensionless parameters in the turbulence model.

usrbd

This applies the boundary conditions. It is given the direction, id, where id = 1 is a boundary at const x, 2, is for y, 3 is for z. The type of boundary is given by bcl[id-1] for the left and bcr[id-1] for the right. Here

bcl, bcr = bcfree if the Start file has FREE
bcl, bcr = bcref if the Start file has SYMMETRY
bcl, bcr = bcper if the Start file has PERIODIC
bcl, bcr = bcfix if the Start file has FIX
bcl, bcr = bcwall if the Start file has WALL

The boundary is on the left for bound=lebound, on the right for bound=rebound. Note that this routine is not called for periodic boundary conditions.

usrcmd

This contains the user defined commands.New commands should be adfded here using the existing code as a template.

usrprt

This prints user parameters.

usrwr

This routine writes user parameters to a model file. Any new parameters that you define should be added to this.Note that the routine write_var is overloaded and comes in six versions for different types of variables:

void write_var(char item[], float value)                 writes the single float, value, with name item
void write_var(char item[], int size, float value[])     writes a float array, value, with name item and size elements
void write_var(char item[], int value);                  writes a single int, value, with name item
void write_var(char item[], int size, int value[]);      writes an integer array, value, with name item and size elements
void write_var(char item[], bool value);                 writes a single bool, value, with name item
void write_var(char item[], char value[]);               writes a string, value, with name item

usrrd

This routine reads user parameters from a model file. Any new parameters that you define should be added to this. As in usrwr, read_var is overloaded and comes in four versions for different types of variables:

void read_var(float *value)       reads a single float or float array, value
void read_var(int *value)         reads a single int or int array, value
void read_var(bool *value)        reads a single bool, value
void read_var(char *value)        reads a string, value

usrsum

This sums variables over the grids with levels chosen by the levs command. It is invoked by the command sum. At present it just sums all the conserved variables. This routine is also useful for examining the whole solution.

usrmon

This function prints variables to the monitoring file set up by the mon command.

usrdef

This function sets the defaults for the user parameters.

usroff

This function sets up the offsets to be used in the solution array. Although there is no reason to do so, these can all be changed except for the gravitational potential, iqpot, which is assumed to be nq-1.


usrquit

This is called whenever a new model is set up, either by the START command or by reading in a model. This is to give the user the opportunity to delete any dynamic arrays that have been defined.

global user variables

Global user variables are defined in user.h. Note that these have to be declared twice, once as extern.

 VISCOSITY, DIFFUSION and THERMAL CONDUCTION (MG_G or MG_MV only)

These are switched on and off by the commands

MG_G>viscous (switch on)
MG_G>noviscous (switch off)

The kinematic viscosity is set by

MG_G>vis value

The scalar diffusion by

MG_G>sdiff value

The thermal conductivity by

MG_G>tcond value

In MG_MV the resistivity is set by

MG_MV>mdiff value

These are used to calculate dynamic coefficients by multiplying by the density in usrmu (except for mdiff).

 ADAPTIVE GRID

Levels 0 and 1 fill the entire domain, but levels 2 and greater only exist where they are needed. Refinement depends on how rapidly the solution varies. For example, whether a level 1 cell is refined to level 2 depends upon the fractional difference between the level 0 and level 1 solution. If this exceeds rtol, then the cell is refined to level 2. Similarly, refinement to level 3 depends on the difference between levels 1 and 2 and so on. Each level has its own timestep subject to the restriction that the timestep on a level n is a power of 2 smaller than that on level 0. If debug is on, then it shows the individual timesteps.Otherwise, all you see is the level 0 timestep if dump is on. There are two commands that control the general behaviour of the adaptive grid.

Remhole

This ensures that there are no holes i.e. no unrefined cells surrounded by refined cells.

Diffbad

A cell that needs to be refined because its error exceeds the tolerance is given a value of qsol = 1. If diffbad is switched on, then nsteps of  a diffusion operator is applied to qsol. A cell is refined if qsol then exceeds refcrit and derefined if it is less than drefcrit. This is designed to ensure that coarse-fine boundaries are smooth.

The number of levels in the adaptive grid is also not fixed. The number of levels can be increased by one by the INCLEV command and decreased by one by the DECLEV command. The coarsest grid (level 0) can be removed by the REMG0 command. This also ensures that the old level 1 is fully refined.

PARALLEL

The code has been parallelized using message passing. For npe processors, the computational domain is partitioned into npe parts by slicing perpendicular to the last coordinate direction that appears in the start command. The partitioning is on the finest grid, which means that parent and child cells near the processor boundaries are not necessarily on the same processor.  The parallel code can be run either under smp or mpi. smp is intended for shared memory machines and for debugging, whereas mpi is needed for clusters.

smp

smp is implemented using Unix sockets and pipes and should run on any Unix machine. To run mg_m with e.g. 4 processors do

smprun -npe=4 mg_m
This will bring up the command prompt in the current window and also start up an xterm for each processor (this requires that xterm be installed). The programme runs exactly as before. There are some additional commands to monitor the parallel behaviour:  PART shows the current partitioning of the domain between processors,  WORK shows the work done by each processor.  The partitioning can be shown graphically by plot proc p. By default, the partitioning is done using timing information from each processor.This can be switched off so that only cell counts are used by NOTIMPART and switched back on by TIMPART. For calculations without gravity, there is little to choose between them, but TIMPART is most appropriate for calculations with gravity since it ensures that the cost of the multigrid Poisson solver is properly taken into account.

mpi

This works exactly the same way, except that it does not bring up xterms for each processor.  To run in interactive mode with e.g. 4 processors do

mpiexec -n 4 mg_m

To run in batch mode, just put the run commands in a file, e.g. do.dat and use this as input to the programme using the normal batch job submission for your installation.

parallel graphics

When running interactively, the graphics works in exactly the same way as for scalar. However, the entire graphics file is on the master processor and may exceed the physical memory size for three dimensional models with fine grids. It may also not be possible to run interactively with enough processors to load a large model. The way to get around this is to use the export and readxq facilities. During a three dimensional batch run you could have e.g.

MG_G>mask z 0.1 export pg plot pg p

in the do.dat file. This will create a copy of the two dimensional plot of pg at z = 0.1 in a file pg.xq. This can later be examined using the readxq command. Note that you can mask when using readxq, but you must use

MG_G>maski id value

where id is the coordinate number (1..nd) and value is the mask value.
